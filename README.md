# cut-pdf-bot

Телеграм-бот, который готовит PDF-книги к чтению на телефоне или электронной книге.

Изначальная задача: книга свёрстана под большой экран, разворотами, и на телефоне читать её
невозможно. Бот режет каждую страницу пополам, поворачивает развороты, а заодно умеет объединять и
сжимать файлы, распознавать сканы и вытаскивать текст в TXT или EPUB.

## Что умеет

| Операция | Что делает |
|---|---|
| ✂️ Разделить страницы | Режет каждую страницу пополам по горизонтали или вертикали. Строго посередине или «с запасом» — чтобы строки на стыке не обрезались |
| 🔄 Повернуть страницы | Поворот всех страниц на 90° в любую сторону |
| 📎 Объединить файлы | Склеивает несколько PDF в один, в порядке отправки |
| 🗜 Сжать PDF | Без потерь (pikepdf) или с пережатием картинок (Ghostscript) |
| 🔍 OCR | Добавляет текстовый слой к сканам — по книге начинает работать поиск |
| 📄 Извлечь текст | Выгружает текст в TXT или EPUB |

Команды: `/start`, `/help`, `/cancel` — отмена работает в любой момент диалога.

## Архитектура

```
Telegram ──► telegram-bot-api ──► bot ──(RabbitMQ)──► worker
                  (2 ГБ)          │                    │
                                  │                    ├─► pypdf / pikepdf
                                  │                    ├─► Ghostscript
                                  │                    └─► ocrmypdf + tesseract
                                  │                    │
                                  └◄──(Redis Stream)───┘
                                       события: прогресс / готово / ошибка
                     общий том /data: файлы между bot и worker
```

Три решения, которые определяют всё остальное:

**Тяжёлая работа уходит в Celery.** Разбор 300-страничной книги — это десятки секунд CPU. В
исходной версии это выполнялось прямо в обработчике, то есть один пользователь блокировал event
loop и всех остальных. Теперь бот только принимает файл и ставит задачу в очередь.

**Файлы не ходят через брокер — ходят пути.** Бот кладёт загрузку в `/data/jobs/<job_id>/` на общем
томе, воркер читает оттуда и пишет результат рядом. В сообщении Celery — только идентификаторы.

**Результат возвращается через Redis Stream, а не pub/sub.** Consumer group переживает перезапуск
бота: запись подтверждается (`XACK`) только после успешного вызова Telegram, а `XAUTOCLAIM` при
старте подбирает всё, что предыдущий процесс не успел обработать. С pub/sub события, отправленные во
время перезапуска, просто пропали бы — и прогресс-бар навсегда замер бы на последнем числе.

Только процесс бота обращается к Telegram API. Воркер к нему не ходит вообще, поэтому вся работа с
rate limit собрана в одном месте — [`tg/progress.py`](src/pdfbot/tg/progress.py).

### Слои

| Каталог | Правило |
|---|---|
| [`domain/`](src/pdfbot/domain/) | Чистая логика. Не импортирует ни aiogram, ни celery. Принимает пути и enum'ы |
| [`tg/`](src/pdfbot/tg/) | Единственное место, где есть aiogram |
| [`worker/`](src/pdfbot/worker/) | Тонкие обёртки: достать запрос, вызвать домен, опубликовать событие |
| [`enums.py`](src/pdfbot/enums.py), [`texts.py`](src/pdfbot/texts.py) | Enum'ы едут в `callback_data`; русский текст живёт только в `texts.py` |

## Запуск

```bash
cp .env.example .env      # впишите BOT_TOKEN, TELEGRAM_API_ID, TELEGRAM_API_HASH
docker compose up --build
```

`TELEGRAM_API_ID` / `TELEGRAM_API_HASH` берутся на <https://my.telegram.org/apps> — они нужны
локальному Bot API серверу, а не самому боту.

Без локального сервера (`USE_LOCAL_BOT_API=false`) бот работает, но Telegram не отдаёт файлы больше
**20 МБ** — а сканы книг обычно тяжелее. Поэтому по умолчанию поднимается свой `telegram-bot-api`,
и лимит вырастает до 2 ГБ.

### Разработка

```bash
make install    # uv sync + pre-commit
make check      # ruff + mypy + unit-тесты
make test-int   # интеграционные тесты (нужен Docker)
```

Нужны Python 3.14 и [uv](https://docs.astral.sh/uv/).

## Тесты

```
tests/unit/         222 теста, без внешних сервисов
tests/integration/    6 тестов, поднимают RabbitMQ и Redis через testcontainers
```

Юнит-тесты гоняют **настоящий** `Dispatcher` — настоящие роутеры, фильтры, FSM и middleware;
подделан только HTTP-сеанс ([`tests/fixtures/telegram.py`](tests/fixtures/telegram.py)). PDF для
тестов генерируются на лету через reportlab, а не лежат бинарниками в репозитории.

Интеграционные тесты не используют `task_always_eager`: он выполняет задачу inline и не задействует
ни сериализацию, ни брокер, ни Redis Stream — то есть ровно то, что и нужно проверить.

## Ограничения, о которых стоит знать

- **Разрезание не уменьшает файл.** Половинки задаются через mediabox/cropbox, содержимое страницы
  не перерисовывается: на выходе вдвое больше страниц примерно того же общего объёма.
- **Сжатие часто ничего не даёт.** Если PDF уже хорошо упакован, бот возвращает оригинал и честно
  об этом пишет, вместо того чтобы выдавать «сжатый» файл того же размера.
- **У OCR прогресс по чанкам.** `ocrmypdf` не умеет сообщать о прогрессе постранично, поэтому книга
  режется на куски по 10 страниц. Цена — чуть больший итоговый файл, чем при одном проходе.
- **Ghostscript под AGPL.** Для личного и портфолио-проекта это нормально; для коммерческого
  распространения — нет.
- **Прогресс-бар обновляется не чаще раза в 2 секунды.** Telegram разрешает примерно одно
  редактирование сообщения в секунду на чат; троттлинг в
  [`domain/progress.py`](src/pdfbot/domain/progress.py) — не косметика.
